1. Introducción y rol del Estudiante 2

El Estudiante 2 es responsable del control y filtrado del tráfico Web (HTTP) de la infraestructura XelajuNetwork mediante el proxy Squid, operando sobre Debian GNU/Linux en modo consola/texto.

Responsabilidades implementadas, conforme a la sección 5 del enunciado:

  • Squid como proxy en modo transparente: no se configura proxy en los navegadores ni en los clientes.
  • Intercepción del tráfico HTTP correspondiente (puerto 80).
  • Filtrado de dominios mediante archivos independientes (admins_blacklist, users_blacklist).
  • Políticas diferenciadas para VLAN ADMIN (192.168.10.0/24) y VLAN USERS (192.168.20.0/24).
  • Registro de solicitudes (auditoría de navegación) y portal de administración para su consulta.
  • Función adicional de routing de tránsito entre E1 (LAN/VLANs) y E5 (Firewall), permitiendo que el tráfico no Web (HTTPS, DNS, DMZ, VPN) fluya sin ser interceptado.

2. Topología y flujo de tráfico

E2 se ubica como nodo de tránsito y filtrado entre E1 (encargado de la segmentación LAN y las VLAN) y E5 (firewall perimetral e IDS):

EnlaceInterfaz E2Par (otro nodo)Red /30
E2 ↔ E1 (downstream, VLANs)192.168.84.1/30R1: 192.168.84.2192.168.84.0/30
E2 ↔ E5 (upstream, salida)192.168.82.2/30E5: 192.168.82.1192.168.82.0/30

Flujo del tráfico:

  • HTTP de LAN → Internet: VLAN → R1 (E1) → E2 (nftables redirige 80 → Squid 3129) → Squid procesa/registra → fetch → E2 → E5 → Internet.
  • HTTPS (443), DNS (53), DMZ, VPN: no se interceptan; transitan por E2 con la IP de origen intacta hacia E5 (enrutamiento normal).

6. Redirección transparente con nftables

Archivo: config/squid-transparent.nft → /etc/nftables.d/, cargado con nft -f y persistente vía /etc/nftables.conf (include "/etc/nftables.d/squid-transparent.nft") + systemctl enable nftables.

  • chain prerouting (nat, dstnat): redirige tcp dport 80 → :3129. Excluye origen VPN (10.200.10.0/24, 10.200.20.0/24) y destino DMZ/VPN (172.16.10.0/24, 10.200.10.0/24, 10.200.20.0/24).
  • chain output (nat, tráfico local): redirige también el HTTP generado en E2, evitando el bucle con la regla meta skuid proxy (uid 13, usuario de Squid en Debian).
  • chain input (filter): refuerza que el portal (8080) solo se acepte desde 192.168.10.0/24 o loopback: tcp dport 8080 ip saddr != 192.168.10.0/24 drop.
  • Idempotencia: el archivo declara la tabla sin cuerpo y luego delete table (sintaxis válida de nftables, sin operadores de shell), permitiendo reaplicación segura.
  • Validación previa: install.sh verifica con nft -c -f antes de aplicar y falla si la sintaxis o la carga no son correctas.

7. Tráfico no procesado por Squid

El tráfico que no corresponde al Web procesado por Squid continúa mediante routing, firewall y Multi-WAN (sección 5 del enunciado):

  • HTTPS (443) y DNS (53) de las VLAN: atraviesan E2 sin interceptar (tránsito) hacia E5.
  • LAN → DMZ (172.16.10.0/24) y LAN → VPN: excluidos de la redirección tanto en nftables como en Squid.
  • VPN (origen 10.200.x): clientes VPN navegando no son interceptados (excepción por origen).
  • Integración E2 ↔ E3 (Multi-WAN): resuelta en ADR-0003; el tráfico de salida conserva la IP del cliente para que E3 aplique sus políticas por IP origen.

13. Problemas encontrados y soluciones

ProblemaSolución
Enlace E1↔E2 sin tráfico: el par visible era la NIC host de R1 (10.0.0.2) y no la VM.R1 puenteó la VM (peer MAC 52:54:00:01:00:01); desde entonces ping 192.168.84.2 = 0 % pérdida y el tráfico de las VLAN llega a E2.
Línea delete table ... 2>/dev/null || true en el archivo nft (sintaxis de shell no válida en nftables) invalidaba la carga futura.Se corrigió al idioma idempotente válido (tabla sin cuerpo + delete table), se validó con nft -c -f y se endureció install.sh para fallar ante reglas inválidas.
Portal aceptaba también el enlace de tránsito E1-E2, contraviniendo el acceso exclusivo a VLAN ADMIN.Se restringió en la aplicación (ALLOWED_NETWORKS) y se reforzó con la chain input de nftables.
Regla redirect errónea para el usuario de Squid (uid).En Debian Squid corre como proxy (uid 13); la cadena output usa meta skuid proxy para evitar el bucle.

14. Dependencias y bloqueantes de integración

  • E1 (resuelto): enlace E1↔E2 operativo y rutas a las VLAN vía 192.168.84.2.
  • E5 (bloqueante externo): 192.168.82.1 responde a nivel L2 pero no responde IPv4 (ping/traceroute 100 % pérdida). Se requiere de E5: (1) levantar 192.168.82.1/30; (2) rutas de retorno 192.168.10/20/30/40.0/24 via 192.168.82.2; (3) no descartar IPv4 en el enlace E2↔E5. Mientras no responda, no se valida el salto final LAN → E2 → E5 → Internet (HTTP permitido, HTTPS y DNS).
  • E3: contrato E2↔E3 definido en ADR-0003 (conserva IP de cliente para políticas Multi-WAN).
  • E4: la exclusión por origen VPN (10.200.x) se valida cuando existan clientes VPN.
